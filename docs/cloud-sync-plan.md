# План: репорты на телефоне и на судовом ПК через облако

Цель: закрытые репорты (и рейсы, к которым они относятся) видны и редактируются
на любом устройстве — телефон, судовой ПК, ноутбук. Облако — единая копия,
устройства работают без интернета и досылают изменения, когда связь появляется.

Вне задачи: напоминания, черновик текущего репорта, ночной режим — остаются
локальными на каждом устройстве. Проект калькулятора груза не трогаем.

## 1. Что есть сейчас

- одно приложение `index.html`, PWA, ставится на телефон и ПК как есть;
- данные в `localStorage`: `noonreport.voyages.v1` (рейсы), `noonreport.entries.v2` (репорты);
- репорт не имеет своего id — он опознаётся по `дата#тип#номер`; у рейса id есть;
- перенос между устройствами — только руками через «Экспорт/Импорт» JSON;
- хостинг Netlify, выкладка перетаскиванием папки `deploy`.

Приложение на телефон уже есть — это PWA. Отдельное «нативное» приложение
не нужно: iOS/Android ставят PWA на экран, оно работает офлайн, данные
установленного PWA Safari не стирает. Решение задачи — не новое приложение,
а слой синхронизации внутри существующего.

## 2. Решение в одну фразу

Локальное хранилище остаётся главным для экрана (offline-first). Добавляем
облачную базу и небольшой модуль синхронизации: «отправить мои изменения —
забрать чужие — пересчитать цепочку». Конфликт решается по времени правки:
кто позже отредактировал репорт, тот и прав.

## 3. Выбор облака

| | Supabase (Postgres) | Firebase Firestore |
|---|---|---|
| Цена для одного пользователя | бесплатно | бесплатно |
| Код в приложении | обычный `fetch`, без библиотек, ~150–200 строк | SDK Google ~250 КБ, нужно кэшировать в офлайн |
| Данные | обычные SQL-таблицы, видно в веб-панели, легко выгрузить | документы, выгрузка только через SDK/консоль |
| Офлайн-очередь | пишем сами (простая: список «неотправленных» id) | встроена в SDK |
| Риск | бесплатный проект ставится на паузу после ~7 дней без запросов; снимается кнопкой в панели, данные не теряются | привязка к Google, менее удобно смотреть данные |

**Рекомендация: Supabase.** Вписывается в стиль проекта (один файл, без сборки
и библиотек), данные в нормальной базе, ту же базу потом можно использовать
для груза. От паузы страхует ежедневный ping (бесплатный GitHub Actions cron
дёргает REST раз в сутки) — ставим и проверяем, что помогает.

Если не хочется думать про паузу вообще — Firestore, план тот же, меняется
только транспорт.

## 4. Данные в облаке

Две таблицы, одна схема на обе. Сам репорт храним как JSON целиком — поля
приложения ещё будут меняться, а менять схему базы каждый раз не хочется.
Несколько полей вынесены в колонки для поиска.

```sql
create table voyages (
  id         text primary key,
  user_id    uuid not null default auth.uid() references auth.users,
  data       jsonb not null,            -- объект рейса как в приложении
  updated_at bigint not null,           -- мс, время правки на устройстве
  deleted    boolean not null default false,
  server_at  timestamptz not null default now()
);

create table entries (
  id         text primary key,
  user_id    uuid not null default auth.uid() references auth.users,
  voyage_id  text not null,
  date       text not null,             -- 'YYYY-MM-DD'
  rtype      text not null,             -- NOON / EOSP / ...
  seq        int  not null default 0,
  data       jsonb not null,            -- репорт целиком (ввод + ручные правки)
  updated_at bigint not null,
  deleted    boolean not null default false,
  server_at  timestamptz not null default now()
);
create index on entries (user_id, server_at);
```

Два разных времени, и это важно:

- `updated_at` — часы устройства, по нему решаем конфликт (новее побеждает);
- `server_at` — часы сервера, по нему устройство спрашивает «что изменилось
  с моего последнего визита». Часы телефона и ПК могут расходиться, часы
  сервера — одни на всех.

Триггер «не затирать новое старым»: upsert с `updated_at` меньше уже
лежащего — молча пропускается, и устройство на следующем pull получит
более свежую версию.

```sql
create function keep_newest() returns trigger language plpgsql as $$
begin
  if new.updated_at < old.updated_at then return null; end if;
  new.server_at := now();
  return new;
end $$;
create trigger voyages_keep_newest before update on voyages for each row execute function keep_newest();
create trigger entries_keep_newest before update on entries for each row execute function keep_newest();
```

Доступ: RLS, каждая таблица — `user_id = auth.uid()`. Один аккаунт
(e-mail + пароль) на все устройства, самостоятельная регистрация в проекте
выключена — чужой не заведёт себе учётку. Публичный `anon`-ключ в
`index.html` — это нормально, защита на RLS.

Удаление — не физическое, а `deleted = true` (надгробие). Иначе второе
устройство, не знавшее об удалении, зальёт репорт обратно.

## 5. Изменения в приложении

### Этап 0. Подготовка данных (без облака, поведение не меняется)

1. Каждому репорту — постоянный `id`. Существующим — детерминированный из
   `рейс + дата + тип + номер`, чтобы один и тот же репорт, лежащий на двух
   устройствах после импорта JSON, получил одинаковый id, а не два разных.
   Новым — `uid()` как у рейсов.
2. Поля `updatedAt` (мс) у репорта и рейса; ставятся при каждом сохранении
   пользователем. Пересчёт цепочки (`recalcChain`) `updatedAt` **не** трогает —
   это производные цифры, не правка.
3. Удалённые репорты/рейсы не выбрасываем из массива сразу, а помечаем
   `deleted` и прячем в интерфейсе; подчищаем после подтверждённой отправки.
4. Экспорт/импорт JSON оставляем — как резервная копия и как путь отката.
5. Поднять версию в `sw.js`, выложить. Внешне ничего не изменилось.

### Этап 1. Облако (делает владелец, я готовлю скрипты)

1. Создать проект Supabase, выполнить SQL из этого файла (таблицы, триггеры, RLS).
2. В Authentication: завести одного пользователя, выключить Sign-ups.
3. Передать мне URL проекта и anon-ключ — они попадут в `index.html`.
4. GitHub Actions cron: раз в сутки `GET /rest/v1/voyages?select=id&limit=1`
   с anon-ключом — защита от паузы.

### Этап 2. Модуль синхронизации в `index.html`

- **Вход**: экран «Облако» (кнопка в шапке): e-mail, пароль, «Войти» —
  один раз на устройство. Токены в `localStorage`, обновление по
  `refresh_token` перед каждой отправкой.
- **Грязный список**: `noonreport.dirty` — id репортов и рейсов, которые
  правили и ещё не отправили. Пополняется в тех же местах, где сейчас
  `persist()` / `saveVoy()`.
- **Push**: все «грязные» одним POST с upsert (`Prefer: resolution=merge-duplicates`).
  Успех → очистить список. Таймаут 15 с через `AbortController` —
  на спутнике не ждём вечно.
- **Pull**: `GET …?server_at=gt.<последний>&order=server_at`, включая надгробия.
  Слияние: пришедшее новее локального (`updated_at`) → заменить; локальное
  «грязное» и не старее → оставить (уйдёт на следующем push); пришло
  надгробие → убрать. Запомнить максимальный `server_at` как «последний визит».
- **После слияния**: `recalcChain()`, `persist()`, перерисовать историю.
  Цепочка «предыдущие показания → текущие» пересчитается сама, как сейчас
  после импорта.
- **Когда запускать**: при старте, по событию `online`, через 2 с после
  любого сохранения, раз в 10 минут, и кнопкой «Синхронизировать сейчас».
  Параллельные запуски не допускаем (один флаг «идёт»).
- **Индикатор** в шапке: `☁ 12:03` (всё отправлено) · `☁ 3 ждут` ·
  `☁ офлайн` · `☁ войти`. Ошибки не всплывают постоянно, видны только на
  экране «Облако».
- **Первое подключение устройства** — явный выбор на экране «Облако»:
  «Отправить мои данные в облако» (для первого устройства) и
  «Заменить мои данные облаком» (для остальных). Порядок внедрения: сначала
  ПК с полной историей → push; потом телефон → заменить облаком. Так не будет
  дублей и вопросов «что откуда».

Объём: ~200 строк в `index.html`, никаких новых файлов и сборки.

### Этап 3. Проверка перед выкладкой

Два браузера (или ПК + телефон), режим «в самолёте»:

1. Создал репорт на телефоне офлайн → включил сеть → появился на ПК.
2. Отредактировал один и тот же репорт на обоих офлайн; вышли в сеть в
   разном порядке → побеждает поздняя правка, цепочка пересчиталась на обоих.
3. Удалил на одном → исчез на другом, не возвращается.
4. Чистое устройство → вход → «заменить облаком» → вся история на месте,
   журнал сходится с ПК.
5. Токен протух (устройство 3 недели без сети) → обновился сам, без повторного входа.
6. Отключить сеть посреди отправки → ничего не потерялось, «грязные» остались, ушли со второй попытки.
7. Старое устройство с версией до синхронизации → обновилось, миграция id прошла, дублей нет.

## 7. Риски и как закрыты

| Риск | Чем закрыт |
|---|---|
| Часы устройств расходятся | конфликт — по `updated_at` устройства, выборка — по `server_at` сервера |
| Дубли после включения на втором устройстве | детерминированные id для старых репортов + «заменить облаком» на втором устройстве |
| Удаление возвращается с другого устройства | надгробия `deleted` |
| Слабый спутниковый канал | таймауты, отправка пачкой, повтор при следующей связи |
| Пауза бесплатного проекта | ежедневный ping; при паузе — кнопка Restore, данные целы |
| Что-то пошло не так | JSON-экспорт остаётся, локальные данные главнее, облако можно пересоздать и залить заново |
